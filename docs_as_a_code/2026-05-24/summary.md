### 抽象構文木（AST）の設計

ASTはコンパイラがプログラムの動作を解釈するために必要な情報のみを保持するデータ構造である。具象構文木との違いを図を用いて確認した。

背景となる概念:

- 具象構文木（Concrete Syntax Tree）は言語の構文を完全に表現し、生成規則と1対1で対応する。括弧などのトークンも全て木にぶら下がる
- 抽象構文木（Abstract Syntax Tree）は実行・評価に必要な情報のみを保持する。括弧のような評価に不要な情報は省略される
- 具体例: `3 + 4 * 5` を AST にすると、頂点が `+`、左が `3`、右が `4 * 5` の木になる。括弧を付けて `3 + (4 * 5)` と書いても評価結果は同じなので、AST では括弧の有無は表現されない
- ASTのノード種類は言語によって決まる。`if` が文か式か、`while` の中身に何が書けるかなどは言語ごとに異なる

Kaleidoscope言語で定義したノード:

- `NumberExprAST`: 数値リテラルを表すノード。`double` のバリューだけを持つ
- `VariableExprAST`: 変数を表すノード。変数名（文字列）を持つ
- `BinaryExprAST`: 二項演算を表すノード。演算子、左辺、右辺を保持する。左辺・右辺はそれぞれ `ExprAST` であり、ぶら下がっている先が何であるかは気にしない（再帰的に評価する）
- `CallExprAST`: 関数呼び出しを表すノード。関数名と引数リスト（`ExprAST` のベクター）を持つ
- `PrototypeAST`: 関数のプロトタイプ（宣言）を表すノード。関数名と引数名のリストを持つ。Kaleidoscope では戻り値は常に `double` なので戻り値型の情報は持たない
- `FunctionAST`: 関数定義を表すノード。プロトタイプとボディで構成される

設計上の議論:

- `FunctionAST` を `name`/`args`/`body` の構成にせず、わざわざ `PrototypeAST` を内包させているのは、後述の `extern` 宣言で `PrototypeAST` を単独で扱うケースがあるため
- `ExprAST` は Go で言うインターフェース的な立ち位置で、各具体ノードはこれを満たす
- RustやScalaなら enum やトレイトでより綺麗に書けそうという話になった。ただしRustで再帰的なAST構造を作る場合は `Box` が必要になり、その点はやや煩雑になりそう
- C++では `std::move` を使ってメモリを移譲しているが、これはC++固有のメモリ管理の都合であり、他言語では別の対応が必要になる

### パーサーの実装

各生成規則に対応するパース関数を定義する方式を採用している。再帰下降構文解析として標準的なアプローチである。

トークンの扱い:

- トークンをグローバルに保持し、`getNextToken()` で次のトークンに進む設計
- トークナイズを先に全て終わらせるのではなく、パースと並行して先頭から順次進める世界観
- `NumVal` や `IdentifierStr` といったグローバル変数に、現在見ているトークンの付随情報が入っている
- 各パース関数は「対応する生成規則のトークンをすべて消費し、次のトークンが準備された状態でリターンする」という規約を守る

主なパース関数:

- `ParseNumberExpr`: 現在のトークンが数値リテラルのときに呼ばれる。`NumVal` を使って `NumberExprAST` を生成し、`getNextToken()` で次に進めてリターン
- `ParseParenExpr`: 開き括弧のときに呼ばれる。`getNextToken()` で `(` を消費し、`ParseExpression()` を呼んで中身を解析し、`)` を確認して消費する。括弧自体はASTノードにならず、`ParseExpression` の結果をそのまま返す
- `ParseIdentifierExpr`: 識別子のときに呼ばれる。次のトークンが `(` でなければ変数として `VariableExprAST` を返し、`(` なら関数呼び出しとして引数を順次パースして `CallExprAST` を返す。これが「先読み」と呼ばれる動作
- `ParsePrimary`: 現在のトークンを見て、数値・識別子・括弧式のいずれかに振り分けるディスパッチャ

設計上のポイント:

- 括弧式が `ParseExpression` を再帰的に呼び出す構造になっており、括弧がネストしていても自然に処理できる
- 識別子が変数なのか関数呼び出しなのかは、次のトークンを見るまで分からない。これを先読みで判定している
- エラー処理は `LogError` 系のヘルパー関数に集約されている

### 演算子優先順位解析

二項演算子を含む式を解析するために、演算子優先順位解析（Operator Precedence Parsing）を採用している。今回最も時間をかけて議論したトピック。

基本的な考え方:

- 式を「プライマリ式」とそれに続く「二項演算子 + プライマリ式」のペアのストリームとして扱う
- 例: `a + b + (c + d) * e * f + g` は、プライマリ `a` の後に `(+, b)`, `(+, (c+d))`, `(*, e)`, `(*, f)`, `(+, g)` というペアが続く列として扱える
- 括弧の中の `c + d` のようなネストした部分式は、`ParsePrimary` から `ParseParenExpr` を通じて再帰的に解析されるため、二項式パーサーは気にしなくてよい

実装の構造:

- 演算子の優先順位はマップで定義し、`GetTokPrecedence()` で取得する。マップになければ `-1` を返して終了条件として使う
- `ParseExpression` はまず `ParsePrimary` で左辺を取得し、その後 `ParseBinOpRHS(0, LHS)` を呼ぶ
- `ParseBinOpRHS(ExprPrec, LHS)` は「消費可能な最小の演算子優先順位」と「現時点の左辺」を受け取る関数

`ParseBinOpRHS` の動作:

- ループの先頭で現在のトークンの優先順位 `TokPrec` を取得し、`ExprPrec` より低ければ即リターン（右辺なし、左辺をそのまま返す）
- 二項演算子を消費して右辺のプライマリ式を取得
- 次のトークンの優先順位 `NextPrec` を見て、現在の演算子より強い場合は右辺をさらに `ParseBinOpRHS(TokPrec + 1, RHS)` で再帰的に拡張する
- そうでなければ `LHS = BinaryExprAST(BinOp, LHS, RHS)` として左辺を更新し、ループを継続

`TokPrec + 1` を渡す理由:

- 例として `a < b * c + d` を考える。`<` の優先順位より強いものは右側にまとめたいが、`*` も `+` も `<` より強いので、`b * c + d` 全体を `<` の右辺にしたい
- このとき `ParseBinOpRHS` を `TokPrec + 1`（= `<` の優先順位 + 1）で再帰呼び出しすると、`*` も `+` もこの閾値以上なので消費を続け、`b * c + d` を1つの部分式としてまとめてくれる
- もしここで `*` の優先順位を渡してしまうと、`*` より弱い `+` がキャンセルされ、`c + d` が右辺に組み込まれなくなる
- 「同じ優先順位より強い演算子のみを右側でまとめる」ための工夫であり、左結合・右結合を適切に処理できる

理解の難しさ:

- アルゴリズムが分かりにくく、コードを目で追うだけでは挙動が直感的に理解しづらい
- 実際にコードを動かしながら確認するのが理解への近道という結論になった

### プロトタイプと関数定義のパース

関数まわりの構文解析を担当する関数群を確認した。

各関数の役割:

- `ParsePrototype`: 関数名と引数リスト `name(arg1 arg2 ...)` をパースする。先頭が識別子でなければエラー、続いて `(` がなければエラー
- `ParseDefinition`: `def` キーワードで始まる関数定義をパースする。`def` を消費し、`ParsePrototype` でプロトタイプを取得し、`ParseExpression` で本体を取得して `FunctionAST` を返す
- `ParseExtern`: `extern` キーワードで標準ライブラリ関数などの宣言をパースする。プロトタイプのみを返す
- `ParseTopLevelExpr`: トップレベルに直接書かれた式を、無名関数（プロトタイプ名が `__anon_expr` 等）として扱うことで `FunctionAST` に統一する

設計の意図:

- `PrototypeAST` を独立して定義しているのは、`ParseDefinition` と `ParseExtern` の両方で再利用するため。前述の `FunctionAST` の構造の伏線がここで回収される
- トップレベル式も無名関数として `FunctionAST` 化することで、後段の処理を統一できる
- `extern sin(arg)` のように標準ライブラリ関数を宣言できるという機能が、この言語にあることが分かった

### 実装の動作確認

パーサーまでのコードをコピーしてビルドし、実際にサンプルコードをパースさせて挙動を確認した。

確認内容:

- 単純な式（`4 + 5;` など）は正しくパースされ、`ParseTopLevelExpr` のログが出力される
- 関数定義（`def foo(x y) x + y;`）も `ParseFunctionDefinition` として処理される
- 改行を含むコードでも、トークナイザが改行・コメントを読み飛ばすため複数の定義をまとめて流せる

`if` 文を含むコードでの挙動:

- 現状の言語仕様には `if` がないため、`def fib(x) if x < 3 then 1 else fib(x-1) + fib(x-2);` のようなコードを与えると、`if` が普通の識別子（変数名）として扱われる
- 結果として `def fib(x) if` までで関数定義として完結したかのように解析され、後続の `x < 3` 以降は別のトップレベル式として処理されてしまう
- `ParseFunctionDefinition` のログが想定外の回数出るなど、観察できる範囲で壊れ方を確認した
- `if` 文の実装は次章以降で対応する想定
