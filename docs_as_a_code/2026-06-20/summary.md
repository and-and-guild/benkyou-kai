## ループエンジニアリングなど

### ループエンジニアリングとは

Addy Osmani の記事「Loop Engineering」を輪読し、ループエンジニアリングの概念とその意味するところを議論した。調査の緊急度が高いという提案があり、今回はこのトピックを軸に進めた。

https://addyosmani.com/blog/loop-engineering/

背景:

- 著者の Addy Osmani は Google に14年在籍するエンジニアで、こうした実力のあるエンジニアが AI を用いた開発のトピックを検証している点に注目した
- 一次情報は英語記事だが、エージェントによる翻訳版を併用して読み進めた（記事の公開は2月7日）

定義と主張:

- ループエンジニアリングとは「エージェントにプロンプトを打つ人間としての自分自身を、それを代わりにやるシステムの設計に置き換えること」である。目的を定義すると、AI が完了するまで反復し続ける
- Peter Steinberger は「コーディングエージェントにプロンプトを打つべきではなく、エージェントにプロンプトを打つループを設計すべきだ」と述べている
- Anthropic で Claude Code に関わる Boris Cherny も「私はもう Claude にプロンプトを与えない。Claude にプロンプトを打ち、次に何をすべきかを判断するループを走らせている。私の仕事はループを書くことだ」と述べている
- これまでの2年ほどは「良いプロンプトを書き、十分なコンテキストを与え、返答を読んで次を打つ」という1ターンごとの付き合い方だったが、それが終わりつつあるという見立てである
- 著者はこれを、エージェントが動く環境そのものを作る「エージェントハーネスエンジニアリング」の一種（ファクトリーモデル）と位置づけている。1年前であれば大量の Bash を書いて自前で維持する必要があったが、今やその部品はプロダクトに標準搭載されつつある

### ループを構成する5つのプリミティブとメモリ

ループには5つの部品と、加えて状態を覚えておく場所（メモリ）が必要であると整理されている。名前はツールごとに多少異なるが、能力としては同じものである。

各プリミティブ:

- **Automation（自動化）**: スケジュールで自動的に発火し、ディスカバリーとトリアージを自分で行う。「ループを一度きりの実行ではなく本当のループにするもの（ハートビート）」と位置づけられている
- **Work（並行作業）**: 複数のエージェントが同じファイルに触れて衝突しないよう、Git worktree で隔離する。同じリポジトリ履歴を共有しつつ独自のブランチを持つ別個の作業ディレクトリを各エージェントに与える
- **Skills**: プロジェクトのコンテキストを毎セッション説明し直さずに済むようにする仕組み。CLAUDE.md やルールに相当する知識を、エージェントが毎回読む場所に書き留める
- **Plugins/Connectors**: MCP 経由で issue トラッカー・データベース・ステージング API・Slack などの実環境ツールにエージェントを接続する。プラグインはコネクタとスキルを束ねるため、同僚がワンクッションでインストールできる
- **Sub-agents**: 作る側と確認する側を構造的に分離する。コードを書いたモデルは自分の宿題を採点するには優しすぎるため、別の（時には異なるモデルの）2つ目のエージェントに検証させる
- **Memory**（6つ目）: マークダウンファイルや Linear のボードなど、一つの会話の外で生き続け「何が終わっていて次が何か」を保持するもの。モデルは実行と実行の間にすべて忘れるため、メモリはコンテキスト内ではなくディスク上に置く必要がある（「エージェントは忘れるが、リポジトリは忘れない」）

セッションをまたぐプリミティブ（記事のテーマに最も近い部分）:

- **SLA ループ**: 一定間隔で再実行する
- **Goal**: 書いた条件が実際に真になるまで走り続ける。各ターンの後で別の小さなモデルが完了を判定するため、コードを書いたエージェント自身が採点者にならない。停止条件は「全テストがパスし、リントがクリーンであること」のように与える
- これらは作業を浮かび上がらせる部分であり、ループの残りはそれに対して動く部分だと整理されている

### CodexとClaude Codeの対応関係

記事は、両ツールがほぼ同じプリミティブを備えており、どちらでも同じループが動くという点を強調していた。

- **Automation**: Codex はオートメーションタブで作成し、プロジェクト・プロンプト・頻度・実行環境（ローカルチェックアウトか背後のワークツリーか）を選ぶ。何かを見つけた実行は inbox に届き、何も見つからなかった実行は自動でアーカイブされる。Claude Code はスケジューリングとフックで同じ地点に到達する（`/loop` で一定間隔の実行、クラウドタスクのスケジュール、フックでライフサイクルの特定タイミングにコマンドを実行、ノート PC を閉じた後も走らせたい場合は GitHub Actions に押し出す）
- **Goal/停止条件**: Codex は同等の機能を SLA ループと呼んでおり、検証可能な停止条件が満たされるまでターンをまたいで動き続ける（一時停止・再開・クリアも可能）。Claude Code の Goal が内部で「真っさらなモデルがループの完了を判定する」構造に相当する
- 形が同じだと気づくと「どのツールがどう」という議論をやめ、どちらでも動くループを設計するようになる、というのが記事の主張である
- 議論では、Claude Code 側のスケジュール指定の粒度（1時間単位など）や Goal 機能の対応状況について、まだ把握しきれていない部分があると確認した

### 設計フェーズにおける「検証可能な停止条件」という課題

記事の停止条件の議論に関連して、参加者の関心が最も高かった論点を掘り下げた。

- リントやテストのように 0/1 で判定できる作業であれば、検証可能な停止条件は素直に定義できる
- しかし設計のような 0→1 のクリエイティブな作業には、こうした明確な停止条件が存在しないことが課題である。むしろそちらをどう扱うかを知りたい、という問題意識が共有された
- コード品質指標（行数、条件分岐の複雑度＝循環的複雑度など）はファイル単位の評価になりがちで、「大枠の筋の良さ」を確認したい目的には合いにくい
- 関連して LayerX の記事が紹介された。サブエージェントの本質はセッション（コンテキスト）を分けられることにあり、メインモデルのアウトプットに対してバイアスなく独立に評価できる点が重要だという理解である。だからこそ agents ディレクトリを切り、システムプロンプトで役割（ロール）を与えることでバイアスをさらに減らせるのではないか、という観点が出た
- 設計を対象とした評価アプローチとしては、LLM-as-a-Judge を使う、同じプロンプトを2回実行して結果の類似度で評価する、といった手法が候補に挙がった

サブエージェントの設計方針についての議論:

- サブエージェントの価値はセッション（コンテキスト）を抱えることにあり、何をさせたいかはエージェント定義よりもスキルを書いて付与すれば十分ではないか、という意見が出た
- 一方で、評価の独立性（バイアス除去）を重視するなら、明示的に役割を与えるエージェント定義にも意味があるのではないか、という対立軸も確認した

### Skillsに関する補足と運用上の注意

記事の Skills の節を読みながら、実運用での挙動について議論した。

- スキルは SKILL.md（メタデータを含む）を収めたフォルダで、任意でスクリプトや参照アセットを加える形式。Codex はコマンドでの呼び出し時やタスクが説明にマッチしたときに自分でスキルを実行する。Claude Code も同じ方式である
- 記事は「気の利いた説明よりも、引き締まった地味な説明の方が勝つ」と述べていた。情報の渡し方のレパートリーを網羅し、正確に言語化された説明の方が読み込まれやすく欠落が少ない、という趣旨だと解釈した
- 実体験として、エージェント共通化のために `agents` 系のディレクトリにスキルを書いたところ、Claude Code が拾わなかったケースがあった。`.claude` 配下に書く必要がある一方、CLAUDE.md に `agents.md` のパスを書いておくと読み込まれる（バケツリレー的な参照）という挙動が共有された

### ループの限界と注意点

記事の後半では、ループが解決しない3つの問題が提示され、ここが最も重要な主張だと受け止めた。

- **検証責任は依然として人間にある**: 「完了」は主張であって証明ではない。無人で走るループは無人で間違いを犯すループでもある。作る側と確認する側を分離する理由のすべては、ループの「完了しました」に意味を持たせるためである
- **理解は放置すると腐る（Comprehension Debt）**: 自分が書いていないコードを速く出荷するほど、存在するものと自分が実際に把握しているものとの差が広がる。ループが作ったものを読まない限り、その差は埋まらない
- **Cognitive Surrender（認知的幸福／降伏）**: ループが返してきたものをそのまま受け取りたくなる心地よい姿勢こそが危険である。ループ設計は、判断を伴って行えば治療薬になり、考えることを避けるために行えば逆効果になる。同じ行為が正反対の結果を生む
- 結論として、レバレッジの危険点が移動しただけで仕事が楽になったわけではない、という整理に共感が集まった。「サボれるところはサボってよいが、理解しなければならないものは理解しろ」という、諦めてよい箇所と悪い箇所のハンドリングがエンジニアの本質だとまとめた

実務での実感:

- 簡単に見えたチケットを AI に任せて出力を確認したら理解が追いつかず、結局自分で読み直して書き直し、自分の開発速度に律速されたという体験が共有された。この「理解を諦めてはいけない」という点が記事の立場と一致する

### TAKTフレームワークの概要

ループエンジニアリングの位置づけを把握した上で、関連 OSS として TAKT（nrslib/takt）を調査・デモした。
https://github.com/nrslib/takt
概要:

- AI コーディングエージェントを再現可能な開発フローとして動かす OSS。正式名称は "TAKT Agent Koordination Topology"（ドイツ語の指揮用語に由来）。作者は YouTube でも発信しているエンジニア（GMO 出身で、ある企業の CTO）
- ループのイテレーション（プラン→実装→レビュー→修正）を YAML のワークフローファイルで宣言的に定義する。一つのエージェントにプロセス全体を覚えさせるのではなく、ステップごとに役割を固定して与える
- ステップごとに Persona・Policy・Knowledge・Instruction・Adapter、そして出力契約（Contract）を割り当てる。必要なエージェントにだけ渡すことでコンテキストの肥大化を防ぐ
- タスクはワークツリーで隔離して実行し、ログとレポートで後から追跡できる
- Claude Code・Claude SDK・Codex SDK・OpenCode SDK・GitHub Copilot CLI・Kiro CLI を、役割・権限・コンテキストの異なるエージェントとして協調させられる
- TAKT 自身も TAKT で開発されている。実装は TypeScript で、AI 特有のコメントが少なく「AI 感がない」点が話題になった

ループエンジニアリング／AIDLC との位置づけ:

- ループエンジニアリングが実装のイテレーションにフォーカスしているのに対し、AIDLC はコンテキストをどう渡し切るか（設計寄り）にフォーカスしている、という対比で整理した
- TAKT は設計を含む1回の実装イテレーションを繰り返す思想で、コンテキスト整備（CLAUDE.md やルール）は利用者側に委ねる雰囲気がある

### TAKTのデモ（絵文字表示機能の追加）

実際に勉強会のプライベートリポジトリで TAKT を動かし、挙動を観察した。

実施内容:

- 「ブログ記事サイトで、記事タイトルの真上に、あらかじめ定義した候補リストからビルドごとにランダムに選んだ絵文字を1つ表示する機能を追加する」というタスクを試した
- アシスタントが対話形式で要件をヒアリングし、雑多なメモから機能要件として言語化してくれた点が好印象だった。既存サイトの構成も調査した上でプランを提示する
- デフォルトのワークフロー YAML（ビルトインカタログ）を使用しており、MAX 30 ステップでプラン・実装・テスト・レビューを回す構成だった。完了するとドラフト PR を作成する流れになっている
- プランのステップは、タグが plan・編集は行わない（edit=no）といったカスタム設定で、Persona や Knowledge（アーキテクチャナレッジ）、Provide Options などが定義されていた

観察された挙動についての所感:

- プランが具体的であれば、OK を出した後の実装は比較的速い
- AI が生成するコードのコメントについて、会話の文脈や「これは使わない」といった作業履歴的な記述をコメントに残してほしくない、宣言的に書いてほしい、という意見が共有された（フェーズをコメントに書きがちな傾向への指摘）

### TAKT運用に関する課題

デモを通じて、チーム運用に向けた懸念点を洗い出した。

現状の課題:

- **完了条件（Condition）の判定があいまい**: プランのルールに「要件が明確で実装可能」といった条件はあるが、それをどう満たしたと判断しているかが見えず、判定が AI 自身の振る舞いに委ねられている部分がある。完了条件をどう満たしているかの明記や定量評価といった、検証を厳密にする機構が一つでもあると採用しやすい
- **セルフチェックのバイアス**: セルフチェック層が「自分の宿題を自分で採点している」ように見える箇所があり、ここはループの限界の議論とも重なる
- **プラン自体の評価機構の不在**: プライベートの単純なリポジトリでは問題なく動いたが、プロダクションコードでは生成されたプランが論理的に破綻したり、存在しない関数を使おうとしたりする可能性がある。計画そのものを丸呑みするのではなく、計画を評価する機構を入れたい
- **プロンプト入力の自由度**: 入力の渡し方はまだ原始的で、雑なメモを構造化してもらう現状のやり方は意図がぶれにくい利点がある一方、自由度を上げすぎるとプランの修正作業が増える。要件・要求・MUST／ベターのグラデーションを構造的に渡せると改善されそうである
- **チームへの浸透の難しさ**: フレームワーク自体は優秀でも、部分的に「使う気にならない」箇所があると広まらない。自分が使う気にならなければ意味がなく、他メンバーが使わなければ意味もない。AI 駆動開発をチームで運用に乗せること自体の難しさが、最大の論点として共有された
- 総じて、現時点では個人開発・プライベート利用に向いている、という評価に落ち着いた
