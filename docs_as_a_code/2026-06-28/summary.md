## AIエージェント開発：Dynamic Workflowなど

### 記事紹介：ものづくりの本質的な難しさ

[Things You Should Never Do（sounds-easy）](https://danluu.com/sounds-easy/) を紹介し、大規模サービス開発の難しさが外部からは見えづらいという点について議論した。

中心的な主張:

- 「大企業の製品なんて自分一人や小さなチームで作れる」という外部からのよくある批判は、問題の複雑さを大幅に過小評価している
- MVP は週末で作れても、ビジネスとして運用するのはそこから先が本番である。MVP の段階では多くの要件を削ぎ落としているため、簡単に見えてしまう

具体例:

- Instagram はバックエンドが Django（Python）で書かれており、フロントエンドは React、バックエンドのコードが数百万行に達している。「写真を見せているだけ」に見えるサービスでもこの規模になる
- 検索エンジンを優れたものとして作ろうとすると、大規模な負荷への対応、言語ごとの正規化（日本語の漢字・ひらがな・カタカナの混在、アラビア語の右書きなど）、セキュリティなど膨大な考慮事項が発生する。MVP なら SQL に放り込んで LIKE 検索で済むが、本番の大規模サービスでは到底そうはいかない
- 開発組織を大きくするほどコミュニケーションのロスが増え、人や時間を投じても効率は上がりにくくなる

気づき:

- UX が優れているほど技術的な複雑さが「見えなくなる」という皮肉がある。スポーツでも上手い人ほど簡単にやっているように見えるのと通じる
- 自分が知らない領域に接するときも、それを軽視してはいけないと再認識した

### AIエージェント開発：Dynamic WorkflowとClaude Code

Claude Code の Dynamic Workflow（動的ワークフロー生成）機能を実際に試し、ループエンジニアリングの仕組みを構築した結果を共有した。

注目ポイント:

- 前回扱ったループエンジニアリング（設計者・実装者・評価者のエージェントに役割分担する構成）を、いちいち自前で組むのは大変だが、Dynamic Workflow を使えば動的にワークフローを生成できる
- 要件の渡し方、設計者・実装者・評価者への分割方針、ループ時にセッションを分けることなど、全体像をあらかじめ定義して Claude Code に指示したところ、JavaScript のスクリプトとしてワークフローの外形を自動生成してくれた
- スコアリングして既定の基準点を超えたら成果物として認める、といったループ条件もスクリプト内に組み込める

スキーマの概念:

- Unit of Work（UoW）：タスク単位。タスクの完了条件や、他の UoW と競合しないかといった情報を持つ
- Inception：UoW の集まりで、バックログのようなイメージ

実行面の特徴:

- バックグラウンドで実行されるため、人間は他の作業を並行できる
- 人間へのエスカレーションが必要な場面では User Question の仕組みで確認を求められる
- 自前でワークフローを組む場合 Mastra や LangChain といったフレームワークもあるが、手軽さの点では Claude Code の Dynamic Workflow で十分という評価

試してみた結果:

- ループの最大思考回数を3回に設定し、LLM-as-a-judge で評価させた。論理的な整合性や AWS の技術的観点での欠落などを指摘し、その指摘事項を元のプロンプトとセットで次のループの設計者に渡す構成にした
- 指摘を考慮すればスコアが上がると見込んでいたが、スコアが全く上がらず一生同じ値のままで、良い成果物として認められずループが機能しない問題が発生した
- 原因の考察（いずれも予想）：評価者エージェントの評価品質や評価者のバイアスの問題。評価者に Sonnet 4.6 相当の安価なモデルを使っていたことが不適切だった可能性。実際の開発でジュニアが書いてシニアがレビューするモデルと照らすと、レビューする側のチューニング余地が大きい。大企業で PR を一人だけにレビューさせることはなく、また指摘を投げるだけでなく示唆出しや具体性を伴い気づきを与えるレビューが望ましいとされる。そうした実際の開発モデルとの対比で雑に作っていたため、何回ループしてもスコアが上がらないのではないか

結論:

- ひな形をサクッと作る用途には非常に便利
- 実運用にはまだ改善の余地がある
- 参考リンク：[Claude Code Monitoring usage](https://code.claude.com/docs/en/monitoring-usage)

### ループエンジニアリングにおける評価の難しさ

ループエンジニアリングで成果物を自動評価する際、実装の評価と設計の評価では難易度が本質的に異なるという点を議論した。

実装の評価は比較的単純:

- 設計がガチガチに決まっていれば、振る舞いとしての答えがあり、技術的な制約もコンテキストとして存在するため、成果物がほぼ一意に定まる
- そのため、安価なモデルの実装者と良い評価者を用意してループをガンガン回せば正解に近づきやすい

設計の評価は本質的に難しい:

- 0→1 の創造的作業であり、多数の制約をすべて満たす新しい発想を出す作業のため、正解が一意に定まらない
- 良いモデルと良い評価者を使わないと前提が成立せず、良いモデルでもクリエイティブな成果物を出せるとは限らない
- 現状できる評価は2種類に限られる：①専門性に振り切った技術的フィードバック（例：設計書の AWS リソースが実在するか、想定コストが AWS のプライシングと合致するかを調べに行く）、②論理的一貫性チェック（入力の指示と出力に矛盾がないか、忠実性があるかを比較する）
- 「設計のまずさは実際に実装してみて初めて気づく」という経験則がある。「ここをこうやるとミスる」という指摘は過去に経験したからこそ言えるもので、AI がその経験を積み重ねるのは難しい。一方で、AI は経験がなくても「こうなってしまいます」という指摘はある程度できる

検討した案:

- 複数の設計者エージェントを並列で動かし、結果をマージ・比較して良いものだけを採用するという案を議論した
- ただし「良い設計を評価して具体的な構成案を出せるなら、その評価者に実装させればよい」というチキンエッグ的な矛盾も指摘された。結局、似たことをやらせるにはマージ・比較の構成にするしかなさそうという見立て
- 参考リンク：[Langfuse LLM-as-a-judge](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge)

### AIエージェントのコンテキスト管理・記憶の仕組み

AIエージェントが「前に言ったことを覚えていない」問題について、その根本原因と理想的な記憶モデルの仮説を議論した。

課題:

- 根本原因はコンテキスト不足にある。「前に言ったやん」という挙動の多くは、過去の内容がコンテキストに入る仕組みになっていないことに起因する
- 一方で、現在のプロジェクト、関わっているリポジトリ、過去に受けたレビュー指摘などをすべてコンテキストに入れると、長すぎて内容がぼやけてしまう

仮説：人間の記憶に近い重み付き忘却モデル:

- 人間がうまくやれているのは、重要度別に少しずつ忘れているからではないか。トータルではコンテキストが短くても、うろ覚えながら大事なことは記憶に残っている状態を表現できるとよい
- 入力（レビュー指摘など）に重要度の重み付けをし、重要なものほど長期記憶として残し、すぐ忘れてよいものは薄れていくようにする
- 時間が経つにつれ徐々に薄まっていく一方、一度忘れかけた情報でも再利用されたらランクを上げる（強化学習的・クリアゲーム的な挙動）
- 例：レビューで受けた指摘が2つあり、次の PR で片方だけ実際に使ったら、そちらの重みを上げて長く覚えておく
- 矛盾する指摘を受けた場合も、重要度をもとに「それは違う」と退けるか「自分の考えと違うがこちらが良い」と採用するかを判断できるべき
- 今後の作業に転用できる抽象度の高いレビューは、ステートフルに長期記憶として保持すべき

期待:

- 実現方法は大きな課題だが、Anthropic がこの課題に対応する機能を近いうちに出してくる可能性を期待している

### オブザーバビリティツールの検討

Claude Code を使ったワークフローでは、Claude がどう思考しどのツールを使ったかが見えづらい（特にヘッドレス実行ではなおさら）。そのためのオブザーバビリティツールを検討・試用した。

Claude Code + OpenTelemetry:

- Claude の思考過程や使用ツールをトレースする OpenTelemetry 連携がある
- ローカルでコンテナを立て、Collector 経由で Grafana に可視化する構成を試している。API キー経由のため課金コストも確認できる


Langfuse:

- Claude Code との連携があり、OpenTelemetry とは別に可視化・評価機能が充実している。GUI がしっかりしている印象
- コンテナでセルフホスト可能だが、PostgreSQL・ClickHouse などの依存があり、セルフホストはやや手間そう。まずは個人がローカルで試して自分の利用内容を分析し、最終的にチームで導入してメンバーの内容を並べて見たい
- トレースやセッションの概念があり、どのくらい時間をかけたかなどを確認できる
- スコアの概念とフィードバック機能（「この回答は役に立ちましたか？」の Yes/No）があり、セッション品質を分析できる
- LLM-as-a-judge でアウトプットを評価できる（ただしジャッジ側も LLM のためコストがかかる）
- Code Evaluators：結果に対してスクリプトを実行しカスタムスコアを出す機能。「結果にこういう内容が入っていてほしい」といった objective なチェックに使い道がありそう
- 活用目的：①トークンコストの集計・削減判断（特定スキルを使ったセッションのコストを分析し、使いすぎなら削る判断ができる。同じスキルを何度も実行していれば意図通りいっていない兆候かもしれない）、②スキル実行の精度改善の糸口
- 参考リンク：[Langfuse LLM-as-a-judge](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge)

現状の課題:

- 「オブザーバビリティを取れた、やったー」で満足しがちで、取得したログやメトリクスをどう精度改善につなげるかの How が不明確。コスト・トークン量は把握できても、性能・精度がどうなっていれば良いのかの判断が難しい

### AIエージェント開発フレームワーク比較

ループのためのワークフローフレームワークやエージェント開発ライブラリをチームで調査し、比較した。

- **Mastra**：TypeScript ベースで Zod と組み合わせて出力スキーマを静的に制約できる点が有用。例えば調査エージェントなら、調査結果の配列、各要素に概要・主張・根拠、根拠オブジェクトに概要とソース URL、といった構造を指定できる。Claude や Perplexity などの API でも出力フォーマット指定はできるが守られないことが多く、Zod なら守られやすく守らなければループを回し直せばよい。Evals 機能があり、カスタムスコアラーも設定できる。スター数は約2.5万。Human in the loop やハーネス系のクラスもある
- **LangChain**：比較的初期からある AI 向けライブラリで、RAG 構築などでよく聞く。Memory Server など多機能。Langfuse とも連携できる
- **Microsoft の Conductor（仮称）**：TACT の上位互換的な位置付けの可能性。最初のコミットが 2025年5月19日と非常に新しく、Copilot で書かれている。Microsoft 製だがスター数は現状微妙
- 参考リンク：[Mastra Evals overview](https://mastra.ai/docs/evals/overview)

理想的な運用イメージとして、Dynamic Workflow でひな形を組み、Mastra などで自分でカスタムし、オブザーバビリティも確保した運用がゴールではないかという見立てを共有した。
